# Container operations (P11)

## Setup and topology

Use Node 24/npm 11 for host tooling and Docker Compose v2. Inspect projects, volumes and occupied ports first. Preserve the selected project name and its volume across updates. Never use volume deletion or prune to fix a startup error.

Fresh setup: `npm ci` then `npm run env:local`. The environment script creates random credentials in a new ignored owner-only `.env` and refuses to overwrite an existing file. An older `.env` needs a valid `JWT_SECRET` added privately before starting the API. Passwords generated by this script are URL-safe hex; if supplying other passwords, URL-encode them for a database DSN (Compose constructs the container DSN from `CLU_DEV_PASSWORD`). Do not print `docker compose config` output containing resolved secrets: use `docker compose config --quiet`.

| Process | Database location |
|---|---|
| Host Node development | `DATABASE_URL`: `localhost:5433/clu_store_dev`, role `clu_dev` |
| API/operator containers | Compose injects `postgres:5432/clu_store_dev`, role `clu_dev` |
| Host tests | `TEST_DATABASE_URL`: `localhost:5433/clu_store_test`, role `clu_test` |

Compose does not pass host `DATABASE_URL` into the API, so host loopback is never mistaken for the database container. PostgreSQL persists under the project's `postgres_data` named volume at `/var/lib/postgresql`. By default only loopback publishes DB 5433 and API 3000. `POSTGRES_HOST_PORT`, `API_HOST_PORT` and `API_BIND_ADDRESS` control mappings; the API always listens on internal `0.0.0.0:3000`. To use a separate instance, consistently supply a private `--env-file` and unique `-p` project name to **every** command, with different published ports.

## DB only: host Node development

```sh
docker compose up -d --wait postgres
npm run db:migrate:dev
npm run db:seed
npm run dev
```

Host development migrations may create a shadow database. Stop on any reset/drift prompt. Test migrations use `npm run db:migrate:test`; tests require the separate guarded test role/database. Starting just `postgres` does not require an API JWT key. Full container startup fails environment validation if that key is missing or invalid.

## All containers: private self-hosting

```sh
docker compose config --quiet
docker compose build
docker compose up -d --wait postgres
# Explicit checked-in migrations; never db push/reset.
docker compose --profile tools run --rm migrate
docker compose up --build -d --wait
curl --fail http://127.0.0.1:3000/health
curl --fail http://127.0.0.1:3000/ready
```

The `tools` profile prevents the one-shot migration job from becoming an automatic startup hook. It uses the pinned Prisma 7 CLI/config, generated client and adapter. `migrate deploy` applies only checked-in migrations and is safe to repeat; review migrations and back up data before applying new ones. The API depends on PostgreSQL health but does not run schema changes or seed at startup. `/ready` checks connectivity, not migration currency: the explicit migration step is required even when readiness is green.

The optional **demo** seed is an explicit operator command, never a production startup step:

```sh
docker compose --profile tools run --rm -e NODE_ENV=development migrate npm run db:seed
```

This override deliberately enables the existing guarded local/demo seed against the selected project's `clu_store_dev`. It refuses production mode, remote/test targets, ID collisions and changed support content. It creates no account/admin. It does not reset data. Use only for a deliberate demo catalog, with provenance reviewed.

Admin provisioning reads operator credentials from stdin, using the existing create-only CLI:

```sh
docker compose --profile tools run --rm -T -e ADMIN_DATABASE_NAME=clu_store_dev migrate npm run admin:create < local-input/admin-credentials.json
```

Keep that input owner-only and ignored, then remove it when no longer needed. Never put passwords into CLI arguments, committed files or image build args.

## Image and shutdown behavior

The Dockerfile uses Debian/glibc Node 24 for both build and runtime. `npm ci --ignore-scripts` uses the lockfile; Prisma generation and TypeScript compilation run explicitly. A build-time Argon2 hash/verify probe checks the native prebuild on the target platform. The runtime contains production dependencies, compiled code and reviewed public media, with no Prisma CLI, TypeScript sources, private environment files or fixtures. The tools target retains development dependencies for explicit operator jobs.

Runtime runs as `node`, with a read-only filesystem, writable temporary mount, dropped capabilities and `no-new-privileges`. Direct Node startup plus Compose init forwards signals. Existing SIGTERM/SIGINT handlers stop accepting HTTP requests, drain active requests and disconnect Prisma within the configured deadline. Compose allows 70 seconds, longer than the maximum validated 60-second application deadline. The image healthcheck uses a bounded `/ready` fetch. A DB outage makes the API unhealthy; Docker health alone does not automatically restart an unhealthy process.

## Logs, restart and updates

```sh
docker compose ps
docker compose logs --tail=100 api postgres
docker compose restart api
docker compose stop api
docker compose up -d --wait api
```

Keep logs private. App logs avoid raw headers/body/query/SQL. Docker administrators can inspect injected environment values, so restrict Docker access. For updates: back up, review code/migration changes, build, apply the explicit migration job, then `docker compose up -d --build --wait`. Images stay local unless an operator separately publishes them. The named DB volume is reused. Rolling back code does not roll back schema/data; review compatibility and restore procedures first. Node/Postgres major tags receive updates; record the resolved image IDs/digests when releasing and review patch refreshes.

## Backup and restore

Backups contain private data. Store them outside the image in an ignored owner-only directory; encrypt and keep an off-host copy according to operator policy. These commands use PostgreSQL's local container connection and do not place a password in arguments:

```sh
mkdir -p local-data/backups
chmod 700 local-data/backups
umask 077
docker compose exec -T postgres pg_dump -U clu_bootstrap -Fc clu_store_dev > local-data/backups/clu-store.dump
# Validate archive readability.
docker compose exec -T postgres pg_restore --list < local-data/backups/clu-store.dump > local-data/backups/archive-list.txt
```

Restore into a **new** database for a drill; never overwrite the live DB as an implicit step:

```sh
docker compose exec -T postgres createdb -U clu_bootstrap -O clu_dev clu_restore_check
docker compose exec -T postgres pg_restore -U clu_bootstrap --exit-on-error --no-owner --role=clu_dev -d clu_restore_check < local-data/backups/clu-store.dump
docker compose exec -T postgres psql -U clu_bootstrap -d clu_restore_check -c 'SELECT count(*) FROM "Product"'
```

Review role privileges and test API behavior against the restored copy before planning any live cutover. No automatic drop/clean or live overwrite is provided. Back up roles separately if provisioning changes; the demo bootstrap init file alone does not represent arbitrary future role changes. Test recovery periodically.

## Troubleshooting and security assumptions

- Port conflict: inspect `docker ps`, `docker compose ls` and listening ports; choose unused published ports and update host DSNs. Do not stop another project.
- Wrong credentials on an existing volume: PostgreSQL init scripts run only for fresh volumes. Changing `.env` does not change existing role passwords. Restore matching private credentials or deliberately rotate the role; do not remove the volume.
- API restart loop: inspect sanitized startup logs for invalid/missing environment field names. Production requires a strong JWT secret. Use an exact CORS origin without a path/trailing slash.
- Healthy DB/ready API but query errors: check `docker compose --profile tools run --rm migrate` and migration history. A connectivity probe does not prove schema availability.
- Empty catalog: seed is explicit and disabled in production mode; a new database has no products until deliberately populated. No fixed admin is provisioned.
- Native loading error: rebuild on the target architecture; do not copy host `node_modules` into Linux. The build probe and container auth smoke must pass.

This package targets private self-hosting. Public DNS, HTTPS/reverse proxy, trusted-proxy policy, shared rate limiting and a stronger token lifecycle remain deployment work. JWT uses HS256 with a default 15-minute TTL; authorization reloads roles. There is no payment processing or inventory reservation. The supplied local database role retains CREATEDB for host shadow migrations; for a hardened public installation, separate runtime/migration ownership and revoke unnecessary privileges through a reviewed operator plan. Restrict bootstrap/test roles and database network access. No cloud deployment or TLS configuration is performed here.

The GitHub workflow uses a fresh run-specific Compose project and random test-only credentials, runs npm ci/lint/typecheck/real PostgreSQL tests/build, then builds and probes the containers after explicit migrations. It publishes no image/artifact and requires no private developer environment. Remote success must be observed in an actual Actions run.
